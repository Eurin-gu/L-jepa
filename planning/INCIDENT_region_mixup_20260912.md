- **发现时间**: 2026-09-12 23:0x

- **严重级别**: 中 (污染了一块**未被 STILT 使用**的缓存; 未污染任何标签)

## 1. 现象

`/mnt/d/lagrangian-jepa-cn/met_cache/era5d/po_valley_italy/` 中 14 个文件的 GRIB bbox
是 **cent_valley_CA** 的范围 `29.0–45.5 N, -128.0–-113.0 E`, 而非 po 的
`38.4–51.9 N, 2.0–18.0 E`:

```

20160219_PL/SFC   20160220_PL/SFC
```

## 2. 根因

`/root/cds_harvester.py` (v1) 硬编码 `REGION = "po_valley_italy"`, 而它收割的 CDS job
覆盖所有区域 → 所有区域的数据都被 `split_grib(out, "po_valley_italy", kind)` 拆进 po 目录.

之所以只污染 14 个文件而不是全部: 这些日期**两区都需要**
(po 的 72h 窗口 20150718–21 与 cent_valley 的 20150719–22 重叠),
po 目录里原本正确的文件被 cent_valley 的同名文件**覆盖**.

## 4. 修复 (三层)

1. **止血** — 禁用 v1 收割器 (`cds_harvester.py.DISABLED`), 启用 v2

2. **数据** — 14 个错误文件移入 `/root/quarantine_badgrib/`; po 的 7 天加入

3. **护栏** — 新增 `/root/bbox_guard.py`, 接入
   `era5_batch.split_grib()` **写完后逐文件校验**, bbox 不匹配即隔离并抛
   `RuntimeError`; `cds_harvester_v2` 收割后再校验一次.
   任何未来的错区数据都不可能在磁盘上静默存活.

## 8. 教训

- **硬编码的区域名是这类事故的唯一来源**; 区域必须从数据自身 (bbox) 推导.
- **"文件存在且体积够大" 不等于 "数据正确"** — 原来的 `have()` 只查体积,
  正好被 44MB 的错区文件骗过. 校验必须查**内容属性** (bbox), 不是文件元数据.
- 覆盖式写入 (`split_grib` 直接 `open(...,"wb")`) 遇到跨区同名日期会静默毁掉正确数据;
  护栏必须放在**写入路径**上, 而不是事后巡检.

## 9. 第二次检查（用户追问："是不是因为当时没有说所有地区都 72h"）

**是，用户的判断正确。** 关键代码化石:

```python
# /root/era5_batch.py  —— 24h 时代的函数, 至今仍在文件里
def needed_days(dates):          # 只算 T-1 和 T  => 24h
    for d in dates:
```

72h 的正确口径在 `plan72.py` 里 (`for k in range(4)` → T-3..T)。这与
`run_batch.py` 的 `--hours` **default=24** 也吻合 —— 72h 是要显式传的。

**时间线**: `cds_harvester.py` v1 的硬编码 `REGION="po_valley_italy"` 写于
**只有 po 一个目标区**的年代 —— 那时硬编码是正确的。之后工作扩展到 6 区并决定
"所有区统一 72h"，v1 **从未被同步修改**，于是继续把所有区的数据写进 po。

## 12. 队列实况

`accepted` 卡在 CDS 服务端 5 个（4×SFC + 1×PL，提交于 22:24–23:33 本地），
它们占据免费额度 → 新请求被拒（`Number queued requests ... temporarily limited`）。

教训补充: **口径变更（24h → 72h、单区 → 6 区）必须全局搜一遍旧口径的残留。**
本例中 24h 时代的 `needed_days()` 和单区时代的硬编码区域名，在决定变更后都还在跑。

## 14. 文件数口径说明（用户问："为什么 11 天是 88 个文件？"）

```
88  =  11  ×  4  ×  2
       │     │     └── 每天 2 个文件: PL(压力层, 37 层 × 6 变量) + SFC(单层, 9 变量)
```

## 16. 第四次检查（用户报："请求失败了"）

### 表象

```
03:19:38  po 201602 PL  Request 44e08129 accepted
06:22:xx  [po_valley_italy] 201602 PL FAIL  (第1次)    ← 异常消息为空
06:22:53  rejected
06:43     rejected   07:03  rejected   07:24  rejected
07:44     rejected   08:05  rejected   08:25  rejected
```

### 根因 1 — 是我们自己的客户端闹钟掐掉了还在排队的 job

`03:19:38 → 06:22` = **3 小时 02 分**, 而 `era5_batch.py` 里 `FETCH_TIMEOUT_S = 10800`
（3 小时）。`_Timeout` 异常的 `str(e)` 是空串，所以日志打出 `FAIL ` 后面什么都没有 ——
这个"空消息失败"就是超时。**服务端那个 job 从未失败**：它一直挂在 CDS 队列里，
`44e08129` 直到 08:48 才开始 running，08:52 成功。

### 根因 2 — 3 个 guard 进程在抢 CDS 免费额度（这才是队列堵死的真因）

`ps` 发现 **3 个 `era5_guard.py`**（pid 811651 / 814611 / 823438，父进程都是 `/init`，
即被 nohup 遗弃的孤儿），启动于 20h / 12h / 3.9h 前。来源是 `era5_chain.sh` 的
第 **[3/3] 重启 guard 持续守护** 一步 —— 该 chain 被跑了多次，每次都孵化一个 guard。

每个 guard 的逻辑是：每 45 分钟**探测一次 CDS**（探测本身就是一次真实请求，占额度），
一旦"恢复"就并发拉起 `era5_72h_fetch.py`（po）和 `era5_batch.py`（**美国 4 区，24h 时代的老管线**）。
于是同一时刻有 **3 个 guard + 1 个 `era5_72all.py`** 四路投递，
把免费账号的排队额度塞满 → 后来所有请求一律 `rejected`。

**旁证 1**: 那 4 个"凭空出现"的 accepted job 创建于本地 04:07 / 04:41 / 04:56 / 05:52，
而下载器在 03:19–06:22 正阻塞在 `44e08129` 上，不可能自己再投 —— 只能是 guard 拉起的脚本投的。
**旁证 2**: `era5_guard.log` 里每一行都**打印两次**，正是两个 guard 同时写同一个文件。

### 修复（四层）

1. 杀掉全部 `era5_guard.py` 及其子任务；
2. **退役** `era5_guard.py` / `era5_72h_fetch.py` / `era5_chain.sh`（改名为 `.RETIRED_20260913`），
   它们已被 `era5_72all.py` 的统一 72h 计划取代；
3. `era5_72all.py` 加 **单实例 flock 锁**（`/root/era5_72all.lock`），重复启动直接退出；
4. `FETCH_TIMEOUT_S` 10800(3h) → **28800(8h)**，并在投递前加**队列闸门**：
   `queue_busy()` 查询 CDS 上 accepted/running 的 job 数，非空就等 15 分钟再投，不再撞墙。

### 验证 — 杀掉 guard 后队列立即流动

```

08:48  状态: {rejected:16, accepted:4, running:1,  successful:79}   ← 44e08129 开始跑
08:52  状态: {rejected:16, accepted:4, successful:80}               ← 44e08129 成功,

```

### 教训

- **同一时刻只能有一个投递者**。需要唯一的进程所有权（flock），而不是靠"记得别多开"。
- **客户端超时必须大于服务端排队延迟**，否则会把仍在排队的任务当成失败而反复重投。
  CDS 免费档的排队延迟实测可达 **5 小时以上**。
- **排队额度是共享资源**：探测探活、多进程竞争都会互相饿死。投递前先看队列再决定。
- 一个"守护脚本自动重启另一个脚本"的链（`chain → guard → batch`）会指数级产生副本，
  必须在每层都加单实例保护。

## 17. ERA5 网格对齐发现（2026-09-13）

### 现象

我们 CDS 下载的 GRIB 网格**纬度不在 ERA5 原生 0.25 网格上**:

```
CDS 网格 lat: 38.40, 38.65, ... , 51.90      (55 点)
原生网格应:   38.50, 38.75, ... , 52.00
偏移: 0.10 度
lon: 2.00 .. 18.00  -> 与原生一致 (2.0 恰为 0.25 的整数倍)
```

### 根因

请求里带了 `"grid": [0.25, 0.25]`，而 `area` 角点 `51.9 / 38.4` 本身不在原生网格上
（`44.4/45.9` 受体范围 + `MARG=6.0` 得到的 51.9/38.4）。CDS 于是把数据**双线性重采样**
到"以请求角点为准"的网格。

**证据**: 把原生网格（GCS 镜像的 raw NetCDF）双线性插值到同一坐标，与 CDS 的 T
逐点比较 —— 8.6 万个点，均值差 **+0.000005 K**，最大 **0.0006 K**。若 CDS 是直接取样，
不可能吻合到这个程度。

**影响**: 我们的气象相对原生 ERA5 有轻微平滑（0.25 度场上可忽略，STILT 本身还会再插值），
但与外部数据做严格对比时必须先插值。

### 已加的开关与护栏

- `era5_batch.area()` 新增 `GRID_MODE`（环境变量 `ERA5_GRID_MODE`）:
  - `anchored`（默认，现状）: 角点即请求角点
  - `native`: 角点**向外**对齐到 0.25 的整数倍 -> 拿原生网格值，不再被重采样

  | 区 | anchored | native |
  |---|---|---|
  | po_valley_italy | 51.9 / 38.4 | **52.0 / 38.25** |
  | cent_valley_CA | 45.5 / 29.0 | 45.5 / 29.0（本就对齐）|
  | north_china_plain | 47.0 / 32.2 | **47.0 / 32.0** |
  | co_front_range | 46.6 / 32.5 | **46.75 / 32.5** |

- 新增**网格一致性护栏** `_check_grid_consistency()`: 新写入文件的网格签名
  `(Ni, Nj, la1, lo1, la2, lo2)` 必须与该区已有文件一致，否则隔离新文件并报错。
  单测已验证: 错网格被拦 + 原文件保住 + 同网格放行。

### 为什么本轮回填**不切**到 native（重要）

**HYSPLIT 要求同一次模拟所用的 4 天气象文件网格完全一致**（72h 回算用 T-3..T）。
已实测确认 po 的 44 个 ARL 文件头完全一致（`ERA5 0 051.900018.0000.250000.250000`）。

因此在一个区里混用两种网格 = 直接破坏 STILT 运行。要切到 native，必须**先把该区
旧文件全部重下**（180 天全部重来，约 2 倍当前成本），而收益只是消除 0.25 度场上
0.10 度偏移带来的轻微平滑 —— **科学上可忽略**。

**决定**: 本轮 72h 回填继续用 `anchored`；`native` 留给下一轮**全新生成**（我们做
10k+ 规模时本来就要重做气象供给）。护栏保证不会有人误混。
